G.1ตอบข้อตัดสินใจ 7 ข้อ
  • ผู้ใช้ตอบ: ขอบเขตรอบแรก, UAT หรือในเครื่อง, เกณฑ์ตัวเลข, rate limit, เครื่องมือ/CI, บัญชี/seed, บริการเสียเงิน
  • บันทึกคำตอบไว้ที่หัวแผน แล้วปรับตารางตามคำตอบ
คำตอบที่ล็อกแล้วผู้ใช้0.5 วัน
G.2ติดตั้งเครื่องมือ
  • ติดตั้ง k6: brew install k6 แล้วจดเวอร์ชัน · clone Takra-GitOps แล้วลองรัน site-smoke.js ตามตัวอย่างใน README ให้ผ่านก่อน
  • เลือกเครื่องยิงที่แยกจากเซิร์ฟเวอร์ที่ทดสอบ ควรเป็น VM ไม่ใช่แล็ปท็อป (ISP บ้านสลับ PoP Cloudflare ทำให้ latency แกว่ง)
  • ตรวจ CPU และเน็ตของเครื่องยิง
k6 พร้อมใช้ บันทึกเวอร์ชันQA0.5 วัน
G.3ตรวจโครงสร้าง test เดิมของทุก repo
  • ดูโฟลเดอร์/ชื่อไฟล์/แท็ก/ชื่อ env ของ Playwright และ Vitest ในแต่ละ repo
  • จดที่วางไฟล์ที่ QA เป็นเจ้าของ และตระกูลชื่อ env ที่ใช้อยู่
  • ถ้าต้องแตะไฟล์ที่ dev เขียน (config, package.json, CI) ให้ถามผู้ใช้ก่อน
บันทึกรูปแบบต่อ repo (ที่วางไฟล์ ชื่อ env)QA0.5 วัน
G.4เขียนกติกากลางลงเอกสาร QA workflow
  • เพิ่มหัวข้อโหลดเทสในเอกสาร QA workflow ของแต่ละ repo (เขียนครั้งเดียว ไม่เขียนซ้ำรายเคส)
  • เขียน mapping แท็ก @load, @smoke, @manual และเกณฑ์ตั้งต้น
  • ขอผู้ใช้อนุมัติก่อนแก้ไฟล์ที่เป็นของ dev
หัวข้อใน qa-test-planning-workflow.md ของแต่ละ repoQA (ถามผู้ใช้ก่อนแตะไฟล์ dev)0.5 วัน
G.5ต่อยอด helper จาก GitOps (เขียนเฉพาะที่ขาด)
  • ใช้ซ้ำ: mint-*.sh ขอ token, lib/config.js host + SLO (hub ใช้ PKCE ผ่าน mint-hub-token.sh เพราะ นโยบายตรวจ aud ใหม่ของ hub บังคับ aud ของ hub-web)
  • เขียนใหม่เฉพาะส่วนที่ GitOps ยังไม่มี: ตัวตรวจ base URL (อนุญาตเฉพาะ UAT/local ปฏิเสธ prod)
  • ตัวตรวจว่า stack เป็น mock ก่อนเริ่ม session (แบบ assertNoRealLive) ถ้าไม่ผ่านให้ throw
  • เพดานจำนวนคำขอฉุกเฉิน และ abort threshold กลาง
  • helper ที่เขียนใหม่วางใน repo ของโปรเจกต์ที่ใช้ (radar, clip) ตามโครงเดิมของ repo นั้น · ai ยังรอผู้ใช้ตอบ
helper ที่ใช้ซ้ำได้ทุกโปรเจกต์ + บันทึกว่าส่วนไหนใช้ของ GitOpsQA0.5 วัน
G.6ขอสิ่งที่ต้องพึ่ง DEV
  • ขอบัญชี/seed จำนวนมากและข้อมูลเริ่มต้นบน UAT
  • ขอสิทธิ์ดูเมตริกบน UAT
  • ขอปรับ/ปิด rate limit ช่วงรอบ stress
  • ขอช่วงเวลาที่ UAT ว่าง
  • ขอตัวเลขผู้ใช้จริงสำหรับกำหนดโหลดปกติ
รายการขอ + คำตอบDEV / PMรอ 1–3 วัน (ขนานได้)
G.7จัดปฏิทิน UAT
  • ตรวจรอบ e2e อัตโนมัติ (เช่น @uat ตอนตี 2) และ session อื่นที่ใช้ UAT เดียวกัน
  • จองช่วงเวลาสำหรับแต่ละโปรเจกต์ ไม่ให้ซ้อนกัน
  • แจ้งทีมล่วงหน้า พร้อมปริมาณโหลดสูงสุด
ตารางช่วงเวลาที่จองแล้วQA / DEV0.5 วัน
G.8ขั้นบังคับทุกรอบ: เช็กสภาพเครื่องก่อนเชื่อผล
  • อ่าน CPU limit/request ของ pod เป้าหมาย และ cpu.stat (throttled/active periods) ก่อนรัน · limit ที่ต่ำ (เช่น 200m) = โควตา 20ms ต่อ 100ms ทำให้ p90/p99 ยาวทั้งที่ CPU ต่ำและไม่มี error
  • จดว่า uat เป็น single-replica ส่วน prod มี HPA · ผลต่อ pod ของ uat เทียบกับ prod ตรงๆ ไม่ได้
  • จด build/commit และ config ที่เกี่ยวข้อง เช่น hub ก่อน/หลัง การปรับ CPU limit เป็นคนละเครื่อง
  • ตัว pool ตรึงจำนวน connection ต่อ DB ไม่ว่าจะกี่ replica · คำนวณ VU ให้สอดคล้อง
ตารางสภาพเครื่องต่อรอบQA0.25 วัน/โปรเจกต์
G.9ขั้นบังคับทุกรอบ: เก็บเมตริกระหว่างรัน
  • ส่ง k6 เข้า Prometheus: --out experimental-prometheus-rw ผ่าน port-forward และต้องตั้ง K6_PROMETHEUS_RW_TREND_STATS="p(95),p(99),avg,max" ไม่งั้นกราฟ latency ว่าง
  • ดู Grafana "Takra — Load Test (k6 + cluster) TAKRA-583": CPU, สัดส่วน throttled (container_cpu_cfs_throttled_periods_total), memory, restarts/OOMKilled
  • เก็บระหว่างรันเท่านั้น ไม่ใช่หลังรัน (เคยอ่านค่า CPU หลังโหลดจบแล้วต่ำกว่าจริงมาก จึงต้องเก็บระหว่างรัน)
  • วัด NLB-direct (ข้าม Cloudflare) เมื่อต้องการเพดานต่อ pod · print %{http_code} เสมอ · แยก warm/cold
  • uat กับ prod ใช้ node ร่วมกัน รอบ destructive ต้องนอกเวลางานและจองใน G.7
