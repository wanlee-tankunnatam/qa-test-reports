แผนโหลดเทส TAKRA — สรุปเพื่อนำเสนอทีม

23 พ.ย. 2026 · เขียนสำหรับ: ทีม DEV / PM / QA · ยังไม่เริ่มเขียนสคริปต์ · ตัวเลขเวลาเป็นค่าประมาณสำหรับ QA 1 คน ต้องให้ทีมยืนยัน

1. วัตถุประสงค์

  • ก่อนปล่อยให้ลูกค้าใช้งานจริง ต้องรู้ตัวเลข ไม่ใช่เดา: ระบบรองรับผู้ใช้พร้อมกันได้เท่าไร ช้าลงที่โหลดเท่าไร พังที่จุดไหน
  • หา เพดานต่อ pod (uat) แล้วประมาณของ prod จากจำนวน replica ที่ HPA ขยายได้
  • ระบุ คอขวด (CPU limit, Postgres, Zitadel, Redis, ClickHouse, คิว, โหนดมีเดีย) และส่งให้ DEV แก้ด้วยตั๋วใน Jira
  • ยืนยันว่า หยุดโหลดแล้วระบบกลับปกติเอง ไม่ต้อง restart ไม่มีทรัพยากรรั่ว
  • ได้ เกณฑ์ผ่าน/ไม่ผ่านที่ตกลงล่วงหน้า เพื่อตัดสิน go/no-go ได้

2. ข้อตกลงเดิม (ไม่ต้องสร้างใหม่)

  • ใช้ harness ใน Takra-GitOps/loadtest เป็นฐาน: k6, mint-*.sh ขอ token, lib/config.js host + SLO, scenario ของ site / insight / hub / central และผลเก่าใน results/ · แผนนี้เป็นชั้นของ QA ที่ครอบด้วยเคสกลาง แท็ก ลำดับ และเกณฑ์
  • ยิงเฉพาะ UAT หรือ stack ในเครื่อง · ไม่ยุ่งกับ prod เลย (ไม่ยิงแม้แต่ baseline อ่านอย่างเดียว) · รอบหนักทำนอกเวลางาน (uat กับ prod ใช้ node ร่วมกัน)
  • ห้ามเปิดไลฟ์จริง/ห้อง TikTok/RTMP จริง · mock ทุกอย่างที่เสียเงินหรือส่งถึงคนจริง · ห้ามยิง UAT/ช่องเดียวกันซ้อน 2 รอบ · ไม่แก้โค้ด dev

5. ทดสอบประเภทอะไรบ้าง

ประเภททำอะไรเกณฑ์/ลักษณะ
Smoke1–5 VU ตรวจสคริปต์ auth และการเก็บเมตริก ถ้าไม่ผ่านห้ามรันขั้นถัดไปทุก scenario ได้ 2xx · helper กันยิง prod/ไลฟ์จริงทำงาน
Baseline5–10 VU นาน 5 นาที ตอนไม่มีโหลดอื่นเส้นฐาน p50/p95/p99 ต่อ endpoint
Loadไล่ขึ้นเป็นโหลดปกติ คงที่ 10–15 นาที แล้วไล่ลงเทียบตารางเกณฑ์ · เกิน 80% ของเกณฑ์ = ผ่านแบบมีความเสี่ยง
Stressเพิ่มทีละ 25% จนเกิน 3–5 เท่าของปกติ หรือเกณฑ์ไม่ผ่านต้องมี abort threshold (เช่น error เกิน 20%) · หาเพดานและจุดคอขวด
Spikeกระโดดเป็น 5 เท่าทันที 2 นาที แล้วลดกลับระบบฟื้นเองโดยไม่ต้อง restart
Soak50–70% ของเพดาน นาน 1–2 ชม.RAM โตไม่เกิน 10% · คิวกลับเป็น 0 · connection ถูกคืน
Capacity NLB-directยิงตรงเข้า NLB ข้าม Cloudflare เพื่อหาเพดานต่อ podเฉพาะ uat นอกเวลางาน · เก็บ CPU/throttle ระหว่างรัน
เฉพาะโปรเจกต์ai: media (ffmpeg) และ SSE/WS ค้างพร้อมกัน · insight/radar/clip: คิวและงานพื้นหลัง · rate limit: ตอบ 429 ถูกต้องและระบบไม่ล้มดูหน้าโปรเจกต์
เกณฑ์ตั้งต้น (ต้องให้ PM/owner ยืนยัน): อ่านเบา p95 < 300 ms · CRUD p95 < 800 ms · query หนัก p95 < 2 s · realtime p95 < 1 s · error < 0.5–1% · ไม่มี 5xx ที่ไม่ใช่ 429 · ไม่มี container restart

8. ความเสี่ยงหลัก

ความเสี่ยงวิธีลด
โหลดกระทบคนอื่นที่ใช้ UAT / ทำให้ prod ช้า (ใช้ node ร่วมกัน)นัดเวลา นอกเวลางาน มี abort threshold และ DEV เฝ้า
CPU limit แบบโควตา ทำ latency tail ที่ไม่เห็นใน CPU graphเช็ก throttled periods ก่อนเชื่อผล · ผลหลังเปลี่ยน limit ถือเป็นคนละเครื่อง
uat single-replica เทียบ prod (HPA) ตรงๆ ไม่ได้สรุปเป็นเพดานต่อ pod แล้วประมาณ prod โดยบอกว่าเป็นค่าประมาณ
เสียเงินหรือส่งถึงคนจริงโดยไม่ตั้งใจmock + helper ตรวจ base URL/mock ก่อนรัน
รอ DEV นาน (seed, สิทธิ์, membership)ขอตั้งแต่สัปดาห์แรก ทำงานอื่นขนานไป
เพดาน rate limit บิดผลวัดแยกวัด 2 รอบ: ปล่อย limiter / ขอ DEV ขยาย

9. ส่งมอบ

  • เคสโหลดในเคสกลางของแต่ละโปรเจกต์ + สคริปต์ k6/ffmpeg ที่ติดแท็ก @load
  • ชีตรายงานใน hub ต่อโปรเจกต์ พร้อมกราฟ p50/p95/p99, RPS, error, CPU/throttle
  • เพดานต่อ pod และการประเมินของ prod, รายการคอขวดเรียงตามผลกระทบ
  • ตั๋วบั๊กใน Jira (ค้นซ้ำก่อนสร้างทุกครั้ง) และข้อเสนอให้ DEV: cache, pool, index, rate limit
  • สรุป PASS / FAIL / ผ่านแบบมีความเสี่ยง ต่อโปรเจกต์
