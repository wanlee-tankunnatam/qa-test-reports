insight.1สำรวจ
  • อ่าน PRD, epics และเอกสารสเปกของโปรเจกต์ เพื่อหา SLA หรือตัวเลขผู้ใช้ที่ระบุไว้
  • อ่านโค้ด backend รายชื่อ controller/route แล้วจัดกลุ่มเป็นโฟลว์ผู้ใช้
  • เลือก endpoint ที่ถูกเรียกบ่อยหรือหนักที่สุด
  • กำหนดสัดส่วน traffic ต่อ scenario (เช่น อ่าน 80% เขียน 20%)
  • หาตัวเลขโหลดปกติจากสถิติจริง ถ้าไม่มีใช้ จำนวนลูกค้า × 3
  • ทำรายการ endpoint ที่ห้ามยิง (เสียเงิน/ส่งถึงคนจริง/ไลฟ์จริง)
รายการ scenario + ตัวเลขเป้าหมายQA—
insight.2เขียนเคสโหลดลงเคสกลาง

  • เพิ่มกลุ่มเคสโหลดต่อ scenario ใส่แท็ก @load (P0 ใส่ @smoke, ต้องมีคนเฝ้าใส่ @manual)
  • ใส่เกณฑ์ผ่าน/ไม่ผ่านที่ต้องเขียนในเคส อ้างจากตาราง threshold กลาง ไม่เขียนซ้ำ
  • ให้ผู้ใช้ตรวจเคสก่อนเริ่มเขียนสคริปต์
เคสในเคสกลางQA → ผู้ใช้0.5 วัน
insight.3ตรวจ schema และ auth ของ ingest

  • ระบุ payload, วิธี auth และ limit ต่อ workspace
  • ยืนยันว่ายิง payload สังเคราะห์ตรงๆ ได้ โดยไม่ต้องดูไลฟ์จริง
สเปก payload สังเคราะห์QA0.5 วัน

insight.11สร้างบัญชี/ข้อมูลเริ่มต้น
  • สร้างหรือขอ DEV seed บัญชีทดสอบจำนวนพอกับ VU สูงสุด (ห้ามบัญชีจริงของลูกค้าและบัญชีต้องห้ามของโปรเจกต์)
  • ตรวจปริมาณข้อมูลใน UAT ให้ใกล้ของจริง ถ้าไม่พอขอ seed เพิ่ม
  • ตั้ง prefix ในชื่อข้อมูลที่โหลดสร้าง เพื่อลบทีหลังได้
  • เก็บ credential ในไฟล์/env ที่ git-ignore ห้ามพิมพ์ลงรายงานหรือ Jira
ชุดบัญชี + ข้อมูลพร้อมใช้QA / DEV0.5 วัน
insight.12เปิดการเฝ้าเมตริกฝั่งเซิร์ฟเวอร์
  • กำหนดเมตริกที่ต้องดู: CPU, RAM, disk I/O, network, connection DB, slow query, ความลึกคิว
  • ขอสิทธิ์ดู dashboard/log บน UAT จาก DEV หรือเตรียมคำสั่งเก็บเอง (docker stats, top)
  • ตั้งวิธีจับคู่เวลาเริ่ม-จบของแต่ละรอบ กับ log ฝั่งเซิร์ฟเวอร์
  • ตรวจว่าเครื่องยิงเองไม่เกิน 70% CPU
แผงเมตริกหรือคำสั่งเก็บเมตริกDEV / QA0.5 วัน
insight.13Smoke
  • รันบน local ก่อน (1–3 VU, 1–2 นาที)
  • ตรวจว่าทุก scenario ได้ 2xx, บัญชีล็อกอินได้, helper กันยิง prod/ไลฟ์จริงทำงาน (ลองใส่ URL ผิดให้ปฏิเสธ)
  • แก้สคริปต์จนผ่าน แล้วจึงรันซ้ำบน UAT
  • ถ้า smoke ไม่ผ่านห้ามรันขั้นถัดไป
smoke ผ่านทุก scenarioQA0.5 วัน
insight.14Baseline
  • รัน 5–10 VU นาน 5 นาที ตอนไม่มีโหลดอื่น
  • บันทึก p50/p95/p99 และ error ต่อ endpoint เป็นเส้นฐาน
  • เก็บ build/commit และขนาดข้อมูลที่ทดสอบ ไว้เทียบตอนทดสอบซ้ำ
  • ถ้าต้องการเพดานต่อ pod ให้วัดแบบ NLB-direct (ข้าม Cloudflare) และจดว่าวัดทางไหน · print %{http_code} เสมอ · แยกผล warm/cold
ตารางเส้นฐานต่อ endpointQA0.25 วัน
insight.15Load
  • แจ้งทีมและเช็คว่าไม่มีรอบอื่นใช้ UAT เดียวกัน
  • ไล่โหลดขึ้นเป็นโหลดปกติ คงที่ 10–15 นาที แล้วไล่ลง
  • เทียบ p95/p99/error กับตารางเกณฑ์
  • บันทึกเมตริกฝั่งเซิร์ฟเวอร์พร้อมกัน
  • จดผลที่เกิน 80% ของเกณฑ์เป็น 'ผ่านแบบมีความเสี่ยง'
  • ไม่ยุ่งกับ prod เลย ไม่ยิงแม้แต่ baseline แบบอ่านอย่างเดียว · รอบโหลดบน uat ให้จองช่วงเวลาใน G.7
  • เช็ก CPU limit และ throttled periods ของ pod เป้าหมายก่อนเชื่อ latency (limit ที่ต่ำ เช่น 200m = โควตา 20 ms ต่อ 100 ms ทำให้ p90/p99 สูงทั้งที่ไม่มี error และ CPU ไม่เต็ม)
ผลเทียบเกณฑ์ + กราฟQA0.5 วัน
insight.16Stress + Spike
  • ตั้ง abort threshold ในสคริปต์ (เช่น error เกิน 20%) ให้หยุดเองก่อนระบบล่มจริง
  • ไล่เพิ่มโหลดทีละ 25% จนเกิน 3–5 เท่าของปกติ หรือจนเกณฑ์ไม่ผ่าน
  • จดจุดที่ latency/error เริ่มพุ่ง = เพดานระบบ
  • Spike: กระโดดเป็น 5 เท่าทันที 2 นาที แล้วลดกลับ
  • ดูว่าระบบกลับมาปกติเองโดยไม่ต้อง restart ไหม
  • ให้ DEV เฝ้าฝั่งเซิร์ฟเวอร์ระหว่างรัน
  • รันนอกเวลางานที่จองไว้ (G.7) เพราะ uat กับ prod ใช้ node ร่วมกัน stress บน uat อาจกระทบ prod
  • uat เป็น single-replica จึงได้เพดานต่อ pod ส่วน prod มี HPA ต้องประมาณจำนวน replica เอง ไม่เทียบตรงๆ
  • จด build/commit และ CPU limit ของรอบนั้น (เช่น hub ก่อน/หลัง การปรับ CPU limitเป็นคนละเครื่อง)
เพดานระบบ + พฤติกรรมตอนพัง/ฟื้นQA (+ DEV เฝ้า)0.5 วัน
insight.17Soak
  • ตั้งโหลด 50–70% ของเพดานที่ได้จาก stress คงไว้ 1–2 ชั่วโมง
  • เก็บแนวโน้ม RAM, connection DB, disk, ความลึกคิว ทุก 1–5 นาที
  • เทียบต้นกับท้ายชั่วโมง: RAM โตเกิน 10% ถือว่าสงสัย memory leak
  • หลังหยุดโหลด ตรวจว่าคิวกลับเป็น 0 และ connection ถูกคืน
กราฟแนวโน้ม + ข้อสรุปQA0.5 วัน
insight.18สรุปรายงาน
  • เทียบผลทุก scenario กับเกณฑ์ ใส่ผ่าน/ไม่ผ่าน/ผ่านแบบมีความเสี่ยง
  • บันทึกเงื่อนไขการรัน: build/commit, สภาพแวดล้อม, ขนาดข้อมูล, config โหลด, เวลา
  • สร้างชีตรายงานใน hub (store แยกตามธรรมเนียม)
  • สรุปใน Jira comment ในนาม Wanlee T ด้วยภาษา 'QA ทดสอบแล้ว…'
ชีตรายงาน + Jira comment (Wanlee T)QA0.5 วัน
insight.19เปิดบั๊กสิ่งที่ไม่ผ่าน
  • ค้น Jira ก่อนสร้างเสมอ: ตั๋วเปิดและปิด ใช้คำไทยและอังกฤษหลายคำ แล้วอ่านผลใกล้เคียงเอง
  • ซ้ำทั้งหน้า/ขั้น/อาการ → ไม่สร้าง ให้คอมเมนต์หลักฐานใหม่ในตั๋วเดิม
  • รากเดียวกันแต่อาการต่าง → สร้างแล้ว relate และบอกว่าอาจแก้พร้อมกันได้
  • หนึ่งปัญหาหนึ่งตั๋ว แนบ scenario, เวลา, กราฟ latency, error ตัวอย่าง, เมตริกเซิร์ฟเวอร์
  • หลังเสร็จชุด ตรวจตั๋วในชุดเดียวกันว่าไม่ซ้ำกัน
ตั๋วบั๊กQA0.5 วัน
insight.20ล้างข้อมูลและปิดรอบ
  • ลบข้อมูล/บัญชีที่โหลดสร้าง (ตาม prefix) และตรวจว่าไม่ปนของคนอื่น
  • คืนค่า rate limit หรือ config ที่ขอ DEV ปรับ
  • แจ้งทีมว่า UAT กลับมาใช้ได้ พร้อมเวลาจบรอบ
UAT สะอาด + แจ้งปิดรอบQA / DEV0.25 วัน
insight.21ทดสอบซ้ำหลัง DEV แก้
  • รันชุดเดิมด้วย config เดิมทุกอย่าง
  • เทียบกับเส้นฐานและผลรอบก่อน
  • อัปเดตตั๋วและรายงานด้วยผลก่อน/หลัง
