แผนการทดสอบ Load Test (ภาพรวม)

วัตถุประสงค์: ประเมินประสิทธิภาพ ความสามารถในการรองรับผู้ใช้ และความเสถียรของระบบภายใต้ภาระงานต่างๆ เพื่อค้นหาขีดจำกัดและจุดที่อาจเกิดปัญหาก่อนเปิดให้บริการจริง · หัวข้อ 1–7 ตามแม่แบบที่ให้มา หัวข้อ 8 ขึ้นไปเป็นส่วนที่เพิ่ม (พื้นสีเหลือง)

1. วัตถุประสงค์ของการทดสอบ

  • ตรวจสอบความสามารถรองรับผู้ใช้พร้อมกัน (Concurrent Users)
  • ตรวจสอบความเร็วในการตอบสนอง (Response Time)
  • ตรวจสอบความสามารถในการประมวลผลคำขอ (Throughput)
  • ตรวจสอบความถูกต้องและครบถ้วนของข้อมูลเมื่อใช้งานพร้อมกัน
  • ตรวจสอบความเสถียรเมื่อได้รับโหลดสูงต่อเนื่อง
  • ค้นหาขีดจำกัดของระบบ (System Capacity) และจุดคอขวด (Bottleneck)
  • ตรวจสอบการฟื้นตัวหลังเกิดโหลดสูงหรือหยุดการทดสอบ

2. ขอบเขตการทดสอบ (Scope)

หัวข้อรายละเอียด
Concurrent Usersทดสอบผู้ใช้พร้อมกันหลายระดับ
API Performanceทดสอบประสิทธิภาพ API
Databaseทดสอบการอ่านและเขียนข้อมูลพร้อมกัน
Response Timeตรวจสอบระยะเวลาตอบสนอง
Throughputตรวจสอบจำนวน Request ต่อวินาที
Error Rateตรวจสอบอัตราการเกิดข้อผิดพลาด
Resource Usageตรวจสอบ CPU, RAM และ Database
System Stabilityตรวจสอบความเสถียรของระบบ

3. ประเภทการทดสอบ

ประเภทวัตถุประสงค์
Load Testทดสอบภายใต้โหลดที่คาดว่าจะเกิดจริง
Stress Testหาขีดจำกัดสูงสุดของระบบ
Spike Testทดสอบเมื่อผู้ใช้เพิ่มขึ้นอย่างรวดเร็ว
Soak Testทดสอบความเสถียรเมื่อใช้งานต่อเนื่องนาน
Scalability Testตรวจสอบการรองรับโหลดที่เพิ่มขึ้นเมื่อขยายทรัพยากร

4. เครื่องมือที่ใช้

Toolวัตถุประสงค์หมายเหตุจากการสำรวจ
k6จำลองผู้ใช้ Load/Stress/Spike/Soakติดตั้งเครื่องยิง (brew install k6) · ใช้ harness ของ Takra-GitOps/loadtest เป็นฐาน (scenario site/insight/hub/central + mint-*.sh + lib/config.js) · k6 ยิง WebRTC/RTSP ไม่ได้ ใช้ ffmpeg กับแทร็ก media ของ ai
Grafanaแสดงผล Metricsมีแล้ว: dashboard "Takra — Load Test (k6 + cluster) TAKRA-583" ในไฟล์ bases/monitoring/dashboards/takra-loadtest-k6.json (k6 RPS/latency + CPU/throttle/memory/restarts) · ต้องขอสิทธิ์เข้าดู
Prometheusจัดเก็บ Metrics จากระบบk6 ส่งเข้า Prometheus ผ่าน remote-write (ที่ DevOps ตั้งไว้) ต้อง port-forward และตั้ง K6_PROMETHEUS_RW_TREND_STATS="p(95),p(99),avg,max" ไม่งั้นกราฟ latency ว่าง · takra-ai มี observability/metrics.ts ต้องตรวจว่าเปิดดูบน UAT ได้ไหม
Postmanตรวจ API และเตรียม Requestใช้ตอนสำรวจ/ลอง request ก่อนเขียนสคริปต์ ไม่ใช้ยิงโหลด
Server MonitoringCPU, RAM, ทรัพยากรเซิร์ฟเวอร์ต้องดู container_cpu_cfs_throttled_periods_total ด้วย (CPU limit เป็นโควตาต่อ 100ms ทำให้ latency tail ทั้งที่ CPU ต่ำ) · เก็บระหว่างรัน ไม่ใช่หลังรัน · ถ้าไม่มี dashboard ใช้ docker stats/top เป็นขั้นต่ำ

5. ตัวชี้วัดผลการทดสอบ

6. ผลลัพธ์ที่คาดหวัง

  • ทราบจำนวนผู้ใช้พร้อมกันที่ระบบรองรับได้
  • ทราบประสิทธิภาพและความเร็วในการตอบสนอง
  • ทราบจุดที่ทำให้ระบบช้าหรือเกิดข้อผิดพลาด
  • ทราบขีดจำกัดของทรัพยากร Server และ Database
  • ระบุ Bottleneck และนำไปปรับปรุงได้
  • มั่นใจว่าระบบเสถียรพอก่อนเปิดใช้งานจริง

7. สิ่งที่ต้องส่งมอบ

  • Test Plan และ Test Scenario → ไฟล์ชุดนี้ + เคสในเคสกลางของแต่ละโปรเจกต์
  • Load Test Script → สคริปต์ k6 ต่อฟีเจอร์ แท็ก @load
  • ผลการทดสอบแต่ละระดับโหลด → ชีตรายงานใน hub
  • Performance Report พร้อมกราฟ
  • รายการปัญหาและ Bottleneck ที่พบ → ตั๋วบั๊กใน Jira
  • ข้อเสนอแนะในการปรับปรุงระบบ
  • สรุปผล PASS / FAIL → ต้องมีเกณฑ์ตัวเลขล่วงหน้า (หัวข้อ 9)

9. เกณฑ์ผ่าน/ไม่ผ่าน (เพิ่ม — จำเป็นสำหรับ PASS/FAIL)

ค่าตั้งต้น ต้องให้ owner ยืนยันหรือปรับตาม SLA จริง · SLO ใน lib/config.js ของ GitOps ต้องตรงกับตารางนี้ (GitOps ระบุว่าต้องให้ PM ยืนยันก่อนรัน)

ชนิด endpointp95p99error
อ่านเบา (me, catalog, health)< 300 ms< 800 ms< 0.5%
CRUD ทั่วไป< 800 ms< 2 s< 1%
query หนัก (dashboard, ค้นหา)< 2 s< 5 s< 1%
อีเวนต์ realtime (SSE/WS)< 1 s< 3 sหลุดไม่เกิน 1%
  • ทุกรอบ: ไม่มี 5xx ที่ไม่ใช่ 429, ไม่มี container crash/restart
  • หลังหยุดโหลด: ระบบ คิว และ connection กลับค่าปกติโดยไม่ต้อง restart
  • soak: memory โตไม่เกิน 10% จากต้นถึงท้าย
  • เกิน 80% ของเกณฑ์ = ผ่านแบบมีความเสี่ยง

10. สภาพแวดล้อมและกฎเหล็ก (เพิ่ม)

  • ยิงเฉพาะ UAT หรือ stack ในเครื่อง ห้าม prod และไม่กระทบ dev app/รอบทดสอบอื่น
  • ห้ามเปิดไลฟ์จริง ห้ามยิงห้อง TikTok/RTMP จริง ใช้ stack mock เท่านั้น
  • ห้ามยิงช่อง/UAT เดียวกันซ้อนกัน 2 รอบ
  • ห้ามยิงส่วนที่เสียเงิน (LLM, TTS, ตรวจสลิป, ชำระเงิน) หรือส่งถึงคนจริง (อีเมล, Telegram) ให้ mock
  • ห้ามแก้โค้ด dev ถ้าต้องปรับ rate limit ให้ขอ DEV ผ่าน env
  • ตัวสร้างโหลดอยู่คนละเครื่องกับเซิร์ฟเวอร์ที่ทดสอบ (ควรเป็น VM ไม่ใช่แล็ปท็อป) และ CPU ไม่เกิน 70%
  • ไม่ยุ่งกับ prod เลย (ไม่ยิงแม้แต่ baseline อ่านอย่างเดียว) · รอบ destructive ทำบน uat นอกเวลางาน เพราะ uat กับ prod ใช้ node ร่วมกัน

11. ข้อมูลและบัญชีทดสอบ (เพิ่ม)

  • บัญชีทดสอบหลายบัญชี ไม่ใช้บัญชีจริงของลูกค้า
  • ปริมาณข้อมูลใน UAT ใกล้ของจริง ไม่งั้น query ดูเร็วเกินจริง
  • ติด prefix ข้อมูลที่โหลดสร้าง และล้างหลังรอบ
  • เก็บ credential ในไฟล์ git-ignore ห้ามใส่รายงาน/Jira

13. ความเสี่ยง (เพิ่ม)

ความเสี่ยงวิธีลด

CPU limit แบบโควตาต่อ 100ms ทำให้ latency tail ที่ไม่เห็นใน CPU graphเช็ก throttled periods ก่อนเชื่อผล (G.8) · ผลหลังเปลี่ยน limit ถือเป็นคนละเครื่อง
