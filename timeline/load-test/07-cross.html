กฎเหล็ก: ยิงเฉพาะ UAT หรือ stack ในเครื่อง ห้าม prod · ห้ามเปิดไลฟ์จริง/ยิงห้อง TikTok/RTMP จริง · ห้ามยิงช่อง/UAT เดียวกันซ้อนกัน 2 รอบ · พอร์ตและโปรไฟล์แยกจาก dev · ห้ามแก้โค้ด dev · ข้าม/mock ทุกอย่างที่เสียเงินหรือส่งถึงคนจริง · เคสลงเคสกลางก่อนสคริปต์ · ชื่อไฟล์ตามฟีเจอร์ ไม่ใส่ชื่อตั๋ว/qa-/ชื่อ worker · แยกชนิดรันด้วยแท็ก @load @smoke @manual · ไฟล์ผลรันชั่วคราว jira-<key>-<ticket>-* ไม่ push · Jira ในนาม Wanlee T เท่านั้น
ของที่ใช้ร่วมกันทุกโปรเจกต์ (จาก GitOps loadtest): cluster ใช้ node ร่วมกันทั้ง uat และ prod · Postgres ใช้ร่วมกันและมีเพดานจำนวน connection (ผ่านตัว pool ยกเว้น central) · Zitadel ใช้ร่วมกัน (ทุกโปรเจกต์ verify JWT แบบ offline จึงอยู่เฉพาะเส้นล็อกอิน/ต่ออายุ token) · uat เป็น single-replica ส่วน prod มี HPA · จุดที่โปรเจกต์กวนกันได้จริงจึงคือ node CPU, Postgres และ Zitadel ไม่ใช่ตัว API เอง · ใช้ zitadel-token-capacity.js วัดเส้นออก token

X.1ออกแบบสัดส่วนผู้ใช้รวม
  • กำหนดจำนวนผู้ใช้พร้อมกันรวม
  • กำหนดสัดส่วนที่เข้าไปยัง ai / rerun (+central) / insight / radar / clip / site ผ่าน Hub · เฉพาะส่วนที่ k6 ยิงได้ ส่วน media ของ ai (ffmpeg) ไม่ปนในรันนี้ ให้เป็นรอบแยกเพราะกิน CPU/NIC ของเครื่องยิงมาก
  • ใช้บัญชีที่เข้า Hub แล้วกระจายไปแต่ละระบบตามโฟลว์จริง (token ของ hub ได้จาก mint-hub-token.sh แบบ PKCE ส่วน insight/central ใช้ mint-uat-token.sh คนละ project id)
  • central จะโหลด hub-api ด้วยเมื่อ runner มี Hub membership ให้นับรวมเป็นโหลดของ Hub

X.2ยืนยันว่าทุกโปรเจกต์ผ่านรอบเดี่ยวแล้ว
  • ทุกโปรเจกต์ผ่านอย่างน้อยรอบ load
  • บั๊กระดับวิกฤตจากรอบเดี่ยวปิดแล้ว
  • ทุกรอบเดี่ยวมีบันทึก G.8 (CPU limit/throttle, replica, build) · ถ้า limit เปลี่ยนหลังรอบนั้น (เช่น hub การปรับ CPU limit) ให้รันรอบเดี่ยวซ้ำก่อน ไม่งั้นเทียบกับโหลดรวมไม่ได้

X.3รันโหลดรวม
  • จองช่วงเวลา UAT ทั้งหมด และให้ DEV เฝ้า
  • รัน load 20 นาที แล้ว stress โดยดูที่ Hub เป็นหลัก
  • ดูว่าโปรเจกต์ไหนกวนกัน (latency ของอีกโปรเจกต์พุ่งตอนอีกตัวหนัก)
  • เฝ้า 3 จุดร่วมระหว่างรัน (G.9): CPU ของ node, จำนวน connection เทียบเพดาน และ pool ของตัว pool, Zitadel ช่วงล็อกอิน/ต่ออายุ token
  • ตรวจ throttled periods ของแต่ละ pod ด้วย (limit ที่ต่ำเจอ throttle ก่อน CPU เต็ม)
  • เป็นรอบ destructive จึงทำบน uat นอกเวลางานเท่านั้น ห้าม prod (uat กับ prod ใช้ node ร่วมกัน ถ้าจะให้ปลอดภัยต้องมี abort threshold และ DEV เฝ้า)
